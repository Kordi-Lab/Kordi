# Database upgrade validation

Run `bash scripts/test-cloud-migrations.sh` before releasing database migration changes. It requires Cargo and uses only synthetic data. By default it creates its own loopback-only PostgreSQL container. With an explicit `KORDI_MIGRATION_PG_BIN`, it creates a new native cluster using a private Unix socket instead. Both modes remove only their own fixture database on exit and never reuse an existing `DATABASE_URL`.

The Rust CI job runs this script as a required step, not an optional or skipped test. On the isolated macOS runner, `scripts/prepare-ci-postgres.sh` builds checksum-pinned PostgreSQL 16.14 inside the job's temporary directory without administrator access. The native fixture listens only on its private socket; no Docker socket access or runner-account permission change is needed. Missing prerequisites fail the check. Production backups and recovery manifests must never be inputs to this synthetic CI job.

The dedicated upgrade tests are explicitly ignored by ordinary unit-test runs. The script supplies a fresh database to each test and explicitly runs them; an absent URL, a non-fixture database, or an existing account schema is an error. Configured chat/runtime integration databases now fail tests on migration errors instead of reporting skipped tests as passes.

## Compatibility contracts

- Pending version 80 uses compatibility SQL that retains historical direct conversation IDs, messages and references, including seed-prefixed history. A database trigger rejects invalid new identities or identity changes, while existing conversations remain editable and can receive new messages. The original released migration file is unchanged.
- Pending version 81 uses compatibility SQL that retains duplicate historical execution rows and their results/events. One active execution, or otherwise the latest completed result, remains the request executor. Other terminal rows are marked `legacy_duplicate`; they cannot become runnable again. New claims retain atomic unique-index admission and return the canonical existing run. The original released migration file is unchanged.
- Multiple live executions for the same identity cause the migration to stop transactionally. Drain those executions before retrying; do not delete or cancel them to force an upgrade.
- Version 89 installs the compatibility contract on databases that already applied the original 80/81 migrations. An existing full executor index is retained so older API instances can continue their upserts during a rolling upgrade. Fresh upgrades use the partial index. Already-deleted historical data cannot be recreated by this compatibility migration.
- The runner neutralizes the historical version-77 group-label cleanup within its migration transaction. The released SQL file remains unchanged; pending upgrades preserve every member's `personal_title` and `preferences_version` as audit data instead of deleting them as cleanup. These fields are not channel display aliases or fallbacks: only an owner or administrator may name a shared channel.
- Pending version 79 fills only null or blank shared names. Every nonempty existing shared name, including an explicitly chosen `Session`, `New chat`, `New session`, or `Untitled session` with case or whitespace variations, retains its exact text, revision, and timestamp. The original released file is unchanged; names already overwritten by a prior release still require verified recovery evidence.
- Version 90 recovers channel names only from matching, authenticated historical `session-title-update` controls in canonical messages. It accepts a nested `sessionTitle.title` or legacy `groupTitle`, verifies the stored sender's authority, and rejects mismatched actors or sessions and malformed controls. Private member labels are never evidence of a shared name, even when members chose identical labels.
- Name repair applies only to an empty shared title or a numbered default whose `updated_at` exactly matches version 79's `applied_at`. Existing shared renames, including an intentionally chosen `Channel N`, remain intact. Without an authenticated public rename, a known default remains in place even if private labels exist; migration must not promote those labels or introduce per-member channel names.
- Version 90 cannot recreate private labels already erased by an earlier version 77. Recovery of those values requires the immutable source backup and separately reviewed reconciliation; do not infer them from other members' names or invent replacements.
- Version checks and migration DDL share a database advisory lock. Each version remains a separate transaction, allowing a failed upgrade to resume without two API replicas applying the same migration concurrently.

The fixture suite covers upgrades from 75, the alternate Digest version-76 history, 88, and 89; concurrent and repeated startup; preserved history and private preferences; authenticated channel-name recovery without overwriting current names; new invalid-identity rejection; duplicate-admission rejection; and safe refusal of multiple live executors. The version-88 fixture executes the actual immutable released SQL rather than a reconstructed schema. Ordinary unit tests pin released versions 77, 79, 80, and 81 by checksum and verify that pending compatibility selection is limited to those versions. Existing chat and Cloud/Desktop execution tests run against another fresh database afterward.

## Production-data rehearsal

Use only a separately authorized, isolated replica within the production security boundary. Never restore production data or credentials into ordinary development, local worktrees, or CI. Keep the source backup immutable and the online production database untouched.

Before upgrading the replica, retain a baseline and verify backup restoration. Compare exact existing-column fingerprints and row counts after migration, with every intended change reviewed. Run migrations without starting application workers; then perform separately scoped functional tests. Do not export raw records, credentials, or unredacted database error reports.

Record semantic invariants before and after the upgrade, not just successful SQL execution: retained private fields and preference revisions remain intact for audit; existing shared names keep their meaning and visibility; only authenticated public rename evidence can restore a shared name; messages and their authorship remain unchanged. Verify that two members with distinct historical private labels see the same shared channel name, and that concurrent or repeated startup makes no further changes. A default-name fill is not harmless if it overwrites an existing shared name or destroys retained data.

## Release gate for incomplete naming history

Stop the release if any previously visible shared channel name becomes a generated default or remains unresolved. Passing SQL and fixture tests alone does not satisfy this gate. Compare the replica against an approved pre-upgrade catalog, including names, ownership, channel identity, and visibility.

When old storage has no verifiable public rename history, require an owner/administrator-reviewed recovery manifest. Keep its conversation identifiers, approved names, source evidence, and expected current revisions inside the authorized production boundary, never in the repository or CI. Do not infer approval from an ordinary member's label or a majority of matching labels. Apply reviewed names through the authorized shared-title operation, or a separately approved transaction with row locks and revision checks; preserve the original records and refresh affected client cursors. The automatic migration must not guess these missing names.

Rehearsal-only reconciliation is not a production fix. Rehearse the same reviewed recovery manifest against a fresh backup, retain the before/after report and rollback inputs, and explicitly approve the production application before cutover. New database columns must not be mistaken for changed historical content when comparing fingerprints: compare the same original columns on both sides.

Passing this rehearsal is not authorization to deploy. Confirm the release scope, active execution drain, backup/restore plan, and maintenance window separately. Older migrations can change data; rolling back only the server image does not undo those changes.
